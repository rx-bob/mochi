# Single File Ruby Loader Architecture (Vite/Rollup Integration)

To make Mochi a first-class citizen in the modern frontend world (Vite, Rollup, Bun), it needs to move away from its current "global bundle" approach (`bundle.js`) to a 1-to-1 **Single File Compilation Model** (`.rb` in -> ES Module `.js` out). 

The biggest challenge with single-file compilation is handling dependencies: Ruby uses global, dynamic `require` resolution, while modern JS bundlers like Vite require a static `import` dependency graph to build, bundle, and hot-reload.

Here is the strategy to bridge the gap and turn Mochi into an intelligent loader for modern JS tooling.

## The Strategy: AST Extraction & JS Import Injection

When a bundler (via `vite-plugin-mochi`) asks the Mochi CLI to compile `counter.rb`, Mochi doesn't just transpile the Ruby to JS. It acts as a bridge between the two module systems.

### 1. Static Analysis (Ruby Side)
Mochi parses the Ruby file (using TreeSitter via `RubyUnderstander`) and extracts all `require "some_file"` or `require_relative "other_file"` statements.

### 2. Import Injection (JS Side)
Mochi translates those Ruby requires into standard ES Module `import` statements and places them at the very top of the generated JavaScript output.

### Example Transformation

**Input (`counter.rb`):**
```ruby
require "./utils/math_helpers"
require "my_gem_dependency"

class Counter
  # ...
end
```

**Output Generated by Mochi CLI:**
```javascript
import { Opal, MochiComponent } from 'mochi-runtime';

// 1. Mochi injects standard JS imports based on the Ruby requires!
// This allows Vite to traverse the graph and hot-reload correctly.
import "./utils/math_helpers.rb"; 
import "my_gem_dependency"; 

// 2. The Opal-transpiled code for JUST this file
Opal.modules["counter"] = function(Opal) { 
  // Opal's internal require still fires, but the module is guaranteed 
  // to be loaded because Vite imported it above.
  self.$require("./utils/math_helpers");
  self.$require("my_gem_dependency");
  // ...
};

// 3. The Web Component Wrapper
class CounterWebComp extends MochiComponent {
  constructor() {
    super();
    this.rubyComp = Opal.Counter.$new();
  }
  // ... Web Component Logic ...
}

// 4. HMR-safe Web Component Registration
if (!customElements.get('my-counter')) {
  customElements.define('my-counter', CounterWebComp);
}

// 5. Export it for Vite
export default CounterWebComp;
```

## Why this works beautifully for Vite/Rollup:

1. **Vite takes over the graph:** Vite sees the `import "./utils/math_helpers.rb";`, realizes it needs that file, and immediately calls the `vite-plugin-mochi` to compile *that* file in isolation. Mochi doesn't have to bundle anything itself.
2. **Perfect Hot Module Replacement (HMR):** If `math_helpers.rb` changes, Vite knows exactly which components depend on it (like `counter.rb`) and can trigger a targeted update for just that branch of the app.
3. **Dead Code Elimination (Tree Shaking):** Vite and Rollup can analyze the full ES Module graph and split the code into optimized chunks, bypassing the performance issues of a monolithic `bundle.js`.

## Handling "Gem" Dependencies
If a user writes `require "faker"`, Mochi outputs `import "faker";`. 
* If `faker` is an NPM package, Vite resolves it natively from `node_modules`.
* If `faker` is a Ruby Gem, the Vite plugin will use Bundler under the hood (e.g., `bundle show faker`) to find the Gem's path on the system, read its `.rb` files, and compile them on the fly.

## Required Structural Changes in Mochi Compiler

To execute this architecture, Mochi's core compiler needs the following capabilities:

1. **A Single-File Command:** `mochi compile-file -i path/to/counter.rb`. It should output pure JS to `stdout` so the Vite plugin can capture it in memory instantly.
2. **Require Extraction:** Update `RubyUnderstander` to extract `require` and `require_relative` calls from the AST.
3. **Isolated Transpilation:** Ensure `QuickJS::Opal::Builder` compiles **just** the AST of that single file into an `Opal.modules[...] = function(...)` string, *without* traversing into the required files.
4. **HMR-Safe Generation:** Update `ComponentGenerator` to output HMR-safe `customElements.define` checks.
5. **Runtime Extraction:** Decouple the Opal Runtime and `MochiComponent` base class from the build process so they can be provided as a standalone `mochi-runtime` NPM package.
